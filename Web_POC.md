# QA Server Auth on Web — POC Brief

Web-focused brief for the QA-server auth work. Everything below reflects the **latest decisions**; mobile-only material (Universal Links / AASA / assetlinks, iOS 17.4 gate, loopback, OldDot/HybridApp bridge, Pusher QA key, server-selector RHP UI, deploy workflow) is intentionally left out. Everything about the popup-transport library — usage constraints, internals, version-pinning risks — lives in `Web_POC_ExpoWebBrowser.md`.

**Status (Jul 23):** the Cloudflare half of the POC is **done and verified**. A real Zero Trust account + mock QA Worker were set up and the whole protocol ran end to end — discovery, dynamic client registration, PKCE authorize via One-time PIN, token exchange, bearer API call, silent refresh with rotation — from both curl and the NewDot dev origin in a browser. §4 is the as-built setup, §5 the findings (all the original unknowns except popup mechanics are answered), §7 the remaining in-app spike.

## 1. Goal

Web and mobile will use the **same Cloudflare Zero Trust auth flow** — explicit OAuth tokens, not cookies. The POC's job is to build that flow into NewDot web and confirm nothing browser-specific breaks. Nobody sees a reason it shouldn't work on web, but experience says something always comes up, so we verify early.

Scope constraint: **no backend integration**. The real QA infra (`qa.exops.io`) doesn't exist for us yet, so the Cloudflare side is mocked with a personal CF account and a Worker standing in for the QA API (see section 4).

## 2. Settled decisions

| Topic | Decision | Rejected alternative |
|---|---|---|
| Web auth | Web uses the same explicit-token flow as native. | Cookie-based auth ("browser handles Zero Trust natively via `CF_Authorization`") — see below for why it lost. |
| `credentials` mode | `credentials: 'omit'` **stays as-is**. Token goes in an explicit `Authorization` header instead. | Letting cookies flow with API fetches. |
| Crypto lib | `react-native-quick-crypto` on native. **Not usable on web**: quick-crypto is C++/Nitro with no react-native-web support. Web uses built-in WebCrypto — `crypto.getRandomValues()` + `crypto.subtle.digest('SHA-256', …)`. Zero new web dependencies, and the PKCE logic still lives in one shared file — see §2.1. | `expo-crypto` (`getRandomBytesAsync` + `digestStringAsync`). |
| Token storage | Tokens live in **Onyx**, same as native. Rationale: we already store authTokens and autogenerated passwords in Onyx, so this adds no new risk class. Cleared on logout. | Cookie-managed session with no app-side storage. |
| Redirect URI | Claimed **https** URLs (RFC 8252). On mobile that means Universal/App Links; **on web it's a same-origin URL** (e.g. `/oauth/callback`). With the popup transport no route/interception is needed — the popup posts the URL back to the opener and gets closed (§3.7); a real route only matters for the deferred full-page fallback. | Custom `expensify://` scheme. |

Why cookies lost: the browser cookie only covers page navigations. Our JS API requests go through `HttpUtils`, which sends `credentials: 'omit'` precisely to avoid CSRF exposure (see the comment at `src/libs/HttpUtils.ts:86-90`), so fetches would never carry `CF_Authorization` anyway. Removing `omit` to make cookies work would reopen CSRF and was vetoed. Explicit header keeps one code path for web + native and touches nothing security-sensitive.

### 2.1 One shared PKCE implementation despite the platform-split crypto lib

Switching from expo-crypto (which has a web build) to quick-crypto (which doesn't) does **not** mean writing the PKCE logic twice. quick-crypto implements the standard WebCrypto API surface — the same one browsers ship natively. Verified against the published `react-native-quick-crypto@1.1.6` source (not just marketing):

- `subtle` is exported as an instance of its `Subtle` class, whose `digest(algorithm, data): Promise<ArrayBuffer>` matches the browser signature, accepts `'SHA-256'` as a plain string (normalized per WebCrypto §18.4.4, same as browsers), and supports SHA-256.
- `getRandomValues(typedArray)` fills and returns the array synchronously, with spec-compliant input validation (integer-typed views only, 65,536-byte quota — mirrors the W3C spec).
- `install()` assigns the whole module to `global.crypto`, but we don't need the global: named imports `{subtle, getRandomValues}` are enough.

So: write the PKCE helper **once** against the standard API, and fork only the provider using the repo's usual `index.ts` / `index.native.ts` pattern (~83 precedents in `src/libs`):

```typescript
// getWebCrypto/index.ts (web) — browser built-in
export default {
    getRandomValues: (arr: Uint8Array) => globalThis.crypto.getRandomValues(arr),
    sha256: (data: ArrayBuffer) => globalThis.crypto.subtle.digest('SHA-256', data),
};

// getWebCrypto/index.native.ts — same API surface from quick-crypto
import {getRandomValues, subtle} from 'react-native-quick-crypto';
export default {
    getRandomValues,
    sha256: (data: ArrayBuffer) => subtle.digest('SHA-256', data),
};
```

Two caveats, both worth keeping in mind:

- **The native side must call the WebCrypto surface, not the Node-style API.** quick-crypto also exposes `createHash('sha256')` etc.; if the native implementation is written against that, web and native genuinely diverge into two implementations. Flag this when the shared helper is built.
- **Install prerequisites (native only, checked against our `package.json`):** quick-crypto@1.1.6 needs peers `react-native-nitro-modules >= 0.31.2` — we already ship `0.35.0` (plus `nitrogen` and our own `ExpensifyNitroUtils` Nitro module, so the ecosystem is established) — and `react-native-quick-base64 >= 3.0.0`, which we **don't** have yet (it would be a second new external dependency to declare). The `expo` / `expo-build-properties` peers are marked optional in `peerDependenciesMeta` and our `expo@56.0.8` satisfies the former anyway. None of this affects web, where the dependency count stays zero.

## 3. The flow, web edition (updated with verified behavior)

Underlying Cloudflare feature: **Access Managed OAuth** (open beta). When enabled on an Access application, Access acts as a standard OAuth 2.0 authorization server: non-browser clients get `401` + `WWW-Authenticate` instead of a `302` to the login page, endpoints are discoverable per RFC 8414/9728, PKCE S256 is supported, and public clients (`token_endpoint_auth_method: "none"`) are allowed — important for a SPA, since we can't ship a client secret in JS. The regular cookie flow keeps working in parallel on the same app (verified: browser navigation → PIN login → cookie; curl → 401 → OAuth).

1. **QA mode active.** Real web auto-detects environment from the URL (`qa.new.exops.io` built with `.env.qa`); there is no server selector on web. For the POC, `QA_EXPENSIFY_URL` (private `.env`) points at the mock Worker — but the app's API root is **not** switched globally (the mock answers everything with `{jsonCode: 200, mock: true}`, so the app would just break noisily). An isolated probe request exercises the same `HttpUtils` path instead; see `Web_POC_Plan.md` §2.
2. **Session check.** Before QA API calls, read `cfSession` from Onyx — settled shape: **one atomic `{accessToken, refreshToken, expiresAt}` object** (shape rationale in `Web_POC_Plan.md` §1; verified refresh-token rotation is why the pair must never be written as two keys). No session → full auth. Expired / near expiry → silent refresh. 401 → refresh as fallback.
3. **PKCE (WebCrypto).** 32 random bytes → base64url without padding = `code_verifier` (43 chars). `code_challenge` = base64url(SHA-256(verifier)), method `S256`. Requires a secure context — fine, dev server is https via mkcert. **Gotcha (from CF's own docs):** regenerate until the challenge starts with `[a-zA-Z0-9]` — a leading `-`/`_` can break CF's URL parameter parsing and yields a confusing `code_challenge_method must be S256 for public clients` error.
4. **Discovery (verified).** Two entry points, both CORS-readable from the browser:
   - Cold start: an unauthenticated QA request returns `401` with `WWW-Authenticate: Bearer realm="OAuth", error="invalid_token", resource_metadata="https://<qa-host>/.well-known/cloudflare-access-protected-resource/<path>"` (RFC 9728). That JSON gives `team_domain` and `authorization_servers`.
   - Direct: `GET https://<team>.cloudflareaccess.com/.well-known/oauth-authorization-server` (RFC 8414). Since the team domain is fixed config, the app can skip the 401 dance and go straight here.
   - Endpoints all live under `https://<team>.cloudflareaccess.com/cdn-cgi/access/oauth/` — `authorization`, `token`, `registration`, `revoke`.
5. **Authorize.** Open `authorization_endpoint` with `response_type=code`, `client_id`, `redirect_uri`, `state`, `code_challenge`, `code_challenge_method=S256`, **and `resource=https://<qa-host>` (RFC 8707)** — CF lists RFC 8707 client support as a prerequisite and the issued token is bound to that resource. The mobile implementation needs it too. On web the transport is `expo-web-browser`'s web implementation (already in `package.json` @ 56.0.5): `openAuthSessionAsync` opens a popup and the callback page calls `WebBrowser.maybeCompleteAuthSession()` — usage constraints and internals in `Web_POC_ExpoWebBrowser.md`. Fallback: full-page redirect with `state`/`code_verifier` parked in `sessionStorage`.
6. **Login.** Real setup: Google `@expensify.com`. POC: One-time PIN email. The Access session on the team domain persists, so subsequent authorizes skip the login screen while it's valid — but the "Authorize Client" consent screen still shows on every authorization request (verified live Jul 27): consent isn't remembered for this public client, so re-auth is one click, never zero.
7. **Callback.** Cloudflare redirects to `https://<web-origin>/oauth/callback?code=…&state=…`. Two cases, and they differ: **popup transport (the POC path)** — the app boots inside the popup, `maybeCompleteAuthSession()` (already at `App.tsx` module scope) posts the URL to the opener and the opener closes the popup; the `/not-found` flash inside the popup is cosmetic, no route or interception needed. One caveat found live: the popup's `window.opener` can come back severed after the redirect chain, which kills the postMessage channel — the shipped recovery is documented in `Web_POC_ExpoWebBrowser.md` §4. **Full-page navigation** — the verified failure mode: the URL falls through the router to `/not-found`, so the deferred full-page fallback (and native deep links) genuinely require interception (web equivalent of the Plaid pattern in `linkingConfig/subscribe.ts`).
8. **Token exchange (verified).** Validate `state`, then `POST token_endpoint` (`application/x-www-form-urlencoded`) with `grant_type=authorization_code`, `code`, `code_verifier`, `redirect_uri` (must exactly match), `client_id`, `resource`. No secret. Response: `{access_token: "oauth:…", refresh_token: "oauth:…", token_type: "bearer", expires_in: 900, scope: "", resource}`. Tokens are opaque (deliberately not JWTs — CF resolves them at the edge and hands the origin a `Cf-Access-Jwt-Assertion` header). Auth codes are single-use and short-lived; a reused/expired code fails with `invalid_grant`.
9. **Persist.** Store in Onyx `cfSession`. Clear on logout.
10. **API requests (verified via curl).** `HttpUtils` attaches `Authorization: Bearer oauth:…` **only** when `isQAServerRequest(url)` matches — exact hostname allowlist, https only, no substring matching. `credentials: 'omit'` untouched. On 401 from a QA host: single-flight `refreshCfToken()`, retry exactly once with freshly built headers, otherwise re-prompt auth. **Refresh (verified):** `POST token_endpoint` with `grant_type=refresh_token`, `refresh_token`, `client_id` (no `resource` needed) → new 900-second access token **and a rotated refresh token** — the old one is spent, so the new one must be persisted immediately and refreshes must be strictly single-flight.

Steps 2-4 and 8-10 are shared logic with native; only steps 5 and 7 have web-specific transport.

const ALLOWED_ORIGIN = 'https://dev.new.expensify.com:8082';

function getCorsHeaders(request) {
    const headers = new Headers({
        'Access-Control-Allow-Methods': 'GET, POST, OPTIONS',
        'Access-Control-Allow-Headers': 'Authorization, Content-Type, X-Requested-With',
        'Access-Control-Max-Age': '86400',
        Vary: 'Origin',
    });

    if (request.headers.get('Origin') === ALLOWED_ORIGIN) {
        headers.set('Access-Control-Allow-Origin', ALLOWED_ORIGIN);
    }

    return headers;
}

export default {
    async fetch(request) {
        const origin = request.headers.get('Origin');

        if (request.method === 'OPTIONS') {
            if (origin !== ALLOWED_ORIGIN) {
                return new Response('Origin not allowed', {status: 403, headers: {Vary: 'Origin'}});
            }
            return new Response(null, {status: 204, headers: getCorsHeaders(request)});
        }

        const url = new URL(request.url);
        const hasAccessAssertion = Boolean(request.headers.get('Cf-Access-Jwt-Assertion'));

        return Response.json(
            {
                jsonCode: 200,
                mock: true,
                method: request.method,
                path: url.pathname,
                // Access resolves the bearer token at the edge and injects the user's
                // JWT here — non-null proves the request came through authenticated.
                authenticatedVia: hasAccessAssertion ? 'Cloudflare Access' : null,
            },
            {headers: getCorsHeaders(request)},
        );
    },
};

## 5. The original unknowns → findings

The "something always comes up" list from before the live run, with verdicts:

1. **CORS on Cloudflare's OAuth endpoints → works, no proxy needed.** From the real NewDot dev origin (`https://dev.new.expensify.com:8082`, DevTools console): the `.well-known` metadata fetch returned a readable `200`, and a token-endpoint `POST` with a dummy code returned a readable `400 {"error":"invalid_grant","error_description":"Invalid authorization code format"}`. A readable error response means CORS is open; the same call with a real code is what the app will do.
2. **401 vs 302 → 401.** With Managed OAuth on, cookie-less non-browser requests get `401` + `WWW-Authenticate` (verified via curl); without it they'd 302 to the login page. Browser navigations still get the cookie flow — both coexist on one app.
3. **Preflights → work** via "Bypass OPTIONS requests to origin" + Worker-side CORS (see §4.5, including the mutual-exclusivity correction).
4. **Popup mechanics → verified in-app, with one real failure mode found and fixed.** The designed path works: popup opens from the press, `maybeCompleteAuthSession()` posts the callback URL, the opener closes the popup. But live (Jul 27, right after a fresh login) the flow hung on an endless spinner: the popup's `window.opener` came back **severed** after the redirect chain, so its completion message was posted into the void and `openAuthSessionAsync` never settled. The shipped recovery watches the localStorage breadcrumb the lib writes before posting, and an openerless popup closes itself — the full story (the lib's internal handshake, what severs openers, why the lib's own fallbacks don't fire on web, why prod's SAML popup never hit this, and the version-pinning risks) lives in `Web_POC_ExpoWebBrowser.md` §3–§5. Both variants now complete end-to-end (scripted browser run, Jul 27). Route interception stays unnecessary for the popup: the `/not-found` flash is cosmetic; interception is confirmed-required **only for the deferred full-page fallback** (verified on a main-window navigation). Two benign consoles inside the popup boot, so nobody chases them: `Failed to load the gib.js script` and a `ChunkLoadError` for the push-notification chunk — side effects of a short-lived popup booting the full app, neither blocks the handshake.
5. **DCR redirect URI rules → accepted.** Registration took the dev origin with the custom `:8082` port without complaint (URI also added to the app's Allowed redirect URIs list).
6. **CSP → fine in dev.** Console fetches to the team domain and Worker were not blocked. The production CSP `connect-src` remains an infra checklist item for the real rollout.
7. **Multi-tab refresh → the risk is real: CF rotates the refresh token on every refresh (verified `refresh_token_rotated: true`).** The old refresh token is spent once used. Consequences: persist the rotated token immediately, keep refresh strictly single-flight, and store the session as one atomic `cfSession` object. Cross-tab coordination is still an open design point; a re-auth papercut is acceptable for a QA-only feature.

Additional protocol facts worth carrying into the implementation:

- **`resource` (RFC 8707) is part of the contract** on authorize and token-exchange requests (not on refresh) — the mobile implementation needs it as well.
- Access token: opaque `oauth:…`, 900 s. The origin never sees it — CF resolves it at the edge and forwards `Cf-Access-Jwt-Assertion` (our Worker echoes this as proof).
- Auth codes are single-use and expire quickly; late exchange fails with `invalid_grant` → restart authorize, don't retry.
- PKCE challenge should start with an alphanumeric character (CF parser quirk, see §3.3).
- The Access session on the team domain outlives the tokens, so re-authorize while it's valid skips the login UI — silent re-auth via hidden iframe/popup may be nearly free, useful if we ever drop refresh-token storage.
- The refresh token is the only long-lived credential (lifetime = "Grant session duration", default = app session duration). Revocation: **Revoke existing tokens** in the Managed OAuth section, or the `revoke` endpoint.

## 6. Success criteria

Already proven at the protocol level (curl + browser console, Jul 23):

- Full round trip: 401 → discovery → DCR → PKCE authorize (One-time PIN) → callback with `code`/`state` on the dev origin → token exchange → `200` from the protected Worker with `Authorization: Bearer oauth:…` and `authenticatedVia: "Cloudflare Access"`.
- Silent refresh: refresh grant returns a fresh 900-second access token (verified working against the API) + rotated refresh token, no user interaction.
- No cookies involved anywhere in the API path; token endpoint reachable cross-origin from the dev origin.

Remaining — must be proven **in-app** by the spike:

- QA API call from NewDot code (not console) triggers the flow via popup or redirect and the retried call succeeds; `credentials: 'omit'` intact in DevTools; non-QA hosts never receive the `Authorization` header.
- One refresh for N parallel 401s (single-flight), rotated token persisted to Onyx before the retry fires.
- Logout clears `cfSession`; next QA call re-prompts.
- Strict Mode double-invocation doesn't open two auth popups (single-flight: concurrent starts share one promise; the PKCE pair is pre-warmed and consumed once).

## 7. Remaining work — the in-app spike

1. **Callback interception — full-page fallback only, deferred.** The popup transport needs no route (§3.7). If the full-page-redirect fallback is ever built, handle `/oauth/callback` before React Navigation resolves it (web equivalent of the Plaid pattern in `linkingConfig/subscribe.ts`) — on main-window navigation it verifiably 404s to `/not-found`.
2. **PKCE helper** on the shared WebCrypto surface (§2.1), with the alphanumeric-start guard.
3. **Config + session:** team domain, `client_id`, QA host allowlist as config; `cfSession` (atomic object) in Onyx, cleared on logout.
4. **`HttpUtils`:** attach bearer only for `isQAServerRequest(url)`; 401 → single-flight refresh (persist rotated token first) → retry once with rebuilt headers → else re-prompt.
5. **Popup transport:** `expo-web-browser` web (`openAuthSessionAsync` + `maybeCompleteAuthSession()`). The operating rules — the popup must open synchronously inside the press's user activation (zero awaits, pre-warmed PKCE pair + Onyx hydration), the severed-opener recovery (breadcrumb watcher raced against the popup promise, `dismissAuthSession()` after the race, popup self-close at boot), and the version-pinned internals behind all of it — live in `Web_POC_ExpoWebBrowser.md` §2–§5. Popup-blocker fallback to full-page redirect with `sessionStorage` stays a contingency; single-flight guards Strict Mode.
6. **Report findings to the mobile and infra owners:** the `resource` param requirement, refresh-token rotation (single-flight + atomic session storage), callback interception requirement, and the Access-CORS/bypass mutual exclusivity for the infra setup.

POC teardown, when the experiment is finished: **Revoke existing tokens** (Managed OAuth section of the Access app), `rm -f /tmp/cf-oauth-tokens.json /tmp/cf-oauth-refreshed.json`, and `unset ACCESS_TOKEN REFRESH_TOKEN AUTH_CODE CODE_VERIFIER` in the terminal. The rotated refresh token is the only credential that outlives 15 minutes.
