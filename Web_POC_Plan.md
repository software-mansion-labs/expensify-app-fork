# Web POC — Implementation Plan

Companion to `Web_POC.md`: that doc says *what* is proven and what's left (§6/§7); this one maps the remaining in-app spike onto concrete files in the repo, in implementation order, and ends with how access is distributed once the branch goes public — a private `.env` handout for testers, Cloudflare roles for collaborators. The branch itself carries only the mechanism; all pointers to the personal Cloudflare account live in the gitignored `.env`. Everything about the popup-transport library (usage constraints, internals, version-pinning risks) lives in `Web_POC_ExpoWebBrowser.md`.

## 0. Groundwork already in the repo (checked, not assumed)

Findings that shrink — or reshape — the spike:

- **The popup-callback problem is mostly already solved.** `src/App.tsx` calls `maybeCompleteAuthSession()` at module scope (line ≈57, added for SAML SSO logout popups). When our OAuth popup loads `/oauth/callback?code=…`, the app boots inside the popup, that call detects it was opened by `openAuthSessionAsync`, posts the URL back to the opener, and closes the window. The `/not-found` fall-through recorded in `Web_POC.md` §3.7 was a *main-window* navigation — in the popup flow the user never sees it. Caveat: the popup loads the entire NewDot bundle before closing (slow but acceptable for a POC; a static callback page is a production optimization, not spike work). **Live correction (Jul 27):** "mostly" earned its hedge — live the popup's `window.opener` came back severed after the redirect chain, the completion postMessage went nowhere, and the flow hung on an endless spinner. The shipped fix watches the localStorage breadcrumb the lib writes before posting (`popupCompletionRecovery.ts` below; full analysis in `Web_POC_ExpoWebBrowser.md` §4).
- **`openAuthSessionAsync` has a working in-repo precedent**: `callSAMLSignOut` in `src/libs/actions/Session/index.ts` (≈line 289) — copy its result-type handling (`result.type !== 'success'` → treat as cancelled), but *not* its catch-and-continue error semantics: SAML logout proceeds to sign out even when the popup fails, whereas a failed auth popup here must abort the flow.
- **Popup timing constraint (`Web_POC_ExpoWebBrowser.md` §2):** `openAuthSessionAsync` calls `window.open` synchronously at invocation and throws `ERR_WEB_BROWSER_BLOCKED` once the browser has revoked the user activation — and awaits alone can revoke it. Consequence: pre-warm the PKCE pair and the Onyx hydration when the menu mounts (button disabled until ready), so the click path has zero awaits before `window.open`. This also reshapes the probe flow (§1) so authentication is *not* triggered from deep inside the 401 path.
- **The staging-server toggle is a 1:1 template** for a future QA-server toggle: `ONYXKEYS.SHOULD_USE_STAGING_SERVER` → `setShouldUseStagingServer` in `src/libs/actions/User.ts` → switch in `src/components/TestToolMenu.tsx` → module-level `Onyx.connectWithoutView` in `src/libs/ApiUtils.ts` (`getApiRoot`). We deliberately do **not** build that toggle in this POC (see §2), but the real integration should mirror it exactly.
- **Zero new dependencies.** Web PKCE runs on built-in WebCrypto; `expo-web-browser` is already a dependency. The `react-native-quick-crypto` (+ `react-native-quick-base64`) install is native-only work and stays out of this spike. Strict Mode is currently off anyway (`USE_REACT_STRICT_MODE_IN_DEV: false` in `src/CONFIG.ts`), so the double-popup guard is belt-and-braces rather than a blocker.

### `src/libs/actions/CloudflareSession.ts` — session state + auth flows (never imports `HttpUtils`)

Onyx writes belong in actions per repo conventions, so the stateful part lives here:

- **A module-level session cache** via `Onyx.connectWithoutView` — the exact pattern `HttpUtils` already uses for `NETWORK` (see `NetworkStore.ts` for the fuller precedent) — exposing a synchronous `getCfSession()` for the request path. Three-state semantics: `undefined` = Onyx not hydrated yet, `null` = hydrated and signed out, object = session. The cache registers a `registerSessionCleanupCallback` (`src/libs/SessionCleanup.ts` — built exactly for module-level caches, cycle-free by design) so sign-out drops it.
- `prepareQAAuthFlow()` + `startQAAuthFlow()` — the prepare half is single-flight and runs at menu mount (hydration + PKCE pair pre-generated so the pair is ready as a value, not a promise); the start half **runs in the click path with zero awaits before `window.open`** — it consumes the pre-warmed pair and calls `openAuthSessionAsync` immediately (§0). There is **no inline-generation fallback** (that await is precisely the activation-voiding hazard): a missing pair fails fast, and the pair is re-warmed *before the flow's promise settles*, so the busy UI can't release into an unprepared second press — cancel → immediate retry stays popup-safe. Single-flight (concurrent callers share one promise, which also covers Strict Mode); on the callback, validate the returned `state` against our generated value **first** — a callback failing provenance is discarded before its `error`/`code` are even read (expo's own localStorage-handle check is not state validation, since the same-origin popup shares localStorage) — then reject an `error=` response and require a non-empty `code`. Then exchange the code and `Onyx.set(ONYXKEYS.CF_SESSION, …)` before resolving. The popup promise is **raced against the §5.4 breadcrumb watcher** (a severed opener leaves `openAuthSessionAsync` pending forever), and `dismissAuthSession()` runs after a success from either channel — it closes the popup where the handle still works and clears expo's localStorage handles either way.
- `refreshCfSession(staleAccessToken?)` — **single-flight** (in-flight join takes precedence, so late callers can't race ahead of persistence) with a staleness guard: when idle and the current token already differs from the one the failing request used, skip the refresh and let the caller retry with the newer token (avoids a wasteful second rotation from late 401s). Persists the rotated refresh token to Onyx *and* the module cache *before* resolving — rotation is verified behavior, the old token is dead the moment the call returns. Returns a **discriminated result** (`refreshed` / `skipped-newer-token` / `reauth-required`), not a boolean — "the session is dead" and "the network blipped" are incompatible outcomes: **terminal failures clear the session and report `reauth-required`** (`invalid_grant` = token spent/revoked; `invalid_response` on a 2xx = CF already rotated but the new pair was unreadable — the stored one is dead either way; keeping a dead session would trap every future press in the retry-refresh branch, never reaching the no-session popup branch), while **transient network failures throw**, keeping the session — callers see an honest failure instead of a false "sign in again".
- `clearCfSession()` — nulls the module cache *synchronously* (a probe right after Clear must not read the dead session), then `Onyx.set(ONYXKEYS.CF_SESSION, null)`. Companion `markCfSessionRejected(token)`: the hook `HttpUtils` calls when a *freshly refreshed* token still gets 401 — drops the session (guarded on the rejected token, so a newer concurrent session is never clobbered) so the next press reaches the popup branch instead of looping refresh → retry → 401.

### `src/libs/actions/CloudflareProbe.ts` — the POC trigger, in its own file to break a cycle

`runQAProbe()` needs `HttpUtils`, and `HttpUtils` needs `refreshCfSession` — housing the probe in `CloudflareSession.ts` would create `CloudflareSession → HttpUtils → CloudflareSession`. A separate probe file keeps the dependency direction one-way.

The probe also owns the auth decision tree, so policy stays out of the network layer:

1. Hydration is a UI-readiness concern, not a click-path await: the buttons stay disabled until `prepareQAAuthFlow()` resolved (§0), so the probe reads the session cache synchronously.
2. No session → `startQAAuthFlow()` immediately — still inside the button press's user activation.
3. Session near/past `expiresAt` → `refreshCfSession()` proactively, then request. If that refresh fails terminally (session cleared), surface "re-auth required" rather than opening a popup — the failed round trip already consumed the user activation; the *next* press lands in branch 2.
4. Request still 401s → `HttpUtils` performs one silent refresh + retry (§2); if the retry 401s again, `HttpUtils` also *drops* the rejected session (token-guarded) before surfacing "re-auth required" — so the probe reports it, and the *next* button press lands in branch 2's popup instead of repeating a doomed refresh → retry → 401 cycle. Background code never opens UI. The whole probe is wrapped in try/catch: popup/exchange/state failures come back as semantic results, never unhandled rejections.
5. Endpoint: `POST /api/CloudflareAuthProbe` (the echo Worker answers any path). Deliberately **not** `/api/OpenApp`: `OPEN_APP` sits in `HttpUtils`' `addSkewList`, so the mock's `Date` header would poison the app-wide time-skew calculation, and startup telemetry also keys off command names.

### `src/types/onyx/CloudflareSession.ts`

`{accessToken: string; refreshToken: string; expiresAt: number}` + export from `src/types/onyx/index.ts`. One atomic object, not separate token keys — refresh rotation means the pair must never be written in two steps (this also resolves the `cfSession` vs `CF_ACCESS_TOKEN`/`CF_REFRESH_TOKEN` inconsistency flagged in `Web_POC.md` §3.2, in favor of the atomic shape).

## 2. Files to change

- **`.env` (local, gitignored) + `.env.example` (committed)** — three new keys. Real values go only in your local `.env`; `.env.example` documents the keys with blank values, so the public branch shows *what* to configure without *where it points*:

```bash
# QA server auth POC — values are distributed privately, ask Sesha for the .env
QA_EXPENSIFY_URL=
QA_CF_TEAM_DOMAIN=
QA_CF_OAUTH_CLIENT_ID=
```

  No build-config changes needed: on web, rsbuild parses the whole `.env` and inlines it into the bundle as `__REACT_WEB_CONFIG__` (`config/rsbuild/rsbuild.common.ts`, with `react-native-config` aliased to `react-web-config`), so new keys are picked up automatically — just restart `npm run web` after editing the file. (`/.env` is confirmed in `.gitignore`, so the values can't be committed by accident.)
- **`src/CONFIG.ts`** — a `QA_AUTH` block reading the three keys through the existing `get(Config, 'KEY', '')` helper with empty-string defaults, same as every other key in that file. Empty values simply mean "QA auth not configured" — clones without the `.env` handout build and run untouched.
- **`src/ONYXKEYS.ts`** — add `CF_SESSION: 'cfSession'` next to the other root keys + the values-type entry (pattern: see `SHOULD_USE_STAGING_SERVER` at ≈line 569 / ≈line 1661). **Mandatory companion change:** categorize the key in `src/libs/ExportOnyxState/common.ts` by adding it to `onyxKeysToRemove` (same reasoning as the `MAPBOX_ACCESS_TOKEN` comment there — `maskFragileData` can't be trusted to catch secrets by field name) and to the matching list in `tests/unit/ExportOnyxStateTest.ts`. The export coverage test fails on any uncategorized new key, so skipping this breaks CI — and it's also what keeps tokens out of exported Onyx state.
- **`src/libs/HttpUtils.ts`** — two changes in `processHTTPRequest`, both silent (the network layer never opens auth UI):
  1. Build a `headers` object only when `isQAServerRequest(url)` matches — compare full `new URL(url).origin` against the configured QA origin (exact origin equality catches lookalike hosts, http downgrades, and port tricks that "https + hostname" checks miss), token read synchronously from the `CloudflareSession` cache. The current `fetch` call passes no headers at all today, so this is additive; `credentials: 'omit'` untouched. OAuth token-endpoint calls never pass through here.
  2. On `401` from the QA origin: `refreshCfSession(tokenUsed)` (single-flight + staleness guard) and retry the request exactly once with rebuilt headers (an internal `isRetry` flag prevents loops), before the generic `!response.ok` error handling. If the retry 401s again, drop the rejected session (token-guarded `markCfSessionRejected`, §1) and reject with the distinct "re-auth required" error; if refresh reports `reauth-required` (no/dead refresh token), same rejection. Transient refresh failures propagate as ordinary network errors instead — "re-auth required" is reserved for sessions that are actually dead. Non-QA 401s keep today's behavior exactly.
- **`src/App.tsx`** — one line next to the existing module-scope `maybeCompleteAuthSession()`: `closeQAAuthPopupIfSeveredOpener()`. The expo call publishes the completion; ours closes the popup that a severed opener can no longer close. Strictly gated (callback path + breadcrumb present + no opener + QA configured), so it's a no-op in the main window, on native, and on clones without the `.env`.
- **`src/components/TestToolMenu.tsx`** — two dev rows: a "Run QA auth probe" `Button` (calls `runQAProbe()`, which checks the session and — when absent — opens the auth popup directly from the press; user activation is why the popup can't open from deep in the network layer) and a "Clear QA session" `Button` (tests the re-prompt criterion). A mount effect runs `prepareQAAuthFlow()`; Run stays disabled until it resolves (readiness is the activation story from §0), and one **shared busy flag** covers both buttons while either operation runs — Clear awaits its Onyx write inside that window. Clear is deliberately *not* gated on PKCE readiness (clearing needs none, and a failed pre-warm must not lock it out); prepare failures surface as an error status rather than a forever-disabled button. The probe's semantic status renders through translated strings, with the raw diagnostic detail appended untranslated (same treatment as raw server errors elsewhere). Follows the existing `TestToolRow` pattern in that file. Both the rows and the effect body are gated on `isQAAuthConfigured()` **and web** — the transport is web-only for now, and on native the effect would hit the throwing crypto stub. Clones of the public branch without the `.env` values see no trace of the feature.
- **`src/languages/en.ts` + the nine non-English locale files** — strings for the rows and the probe statuses. Not just `es.ts`: every locale file (`de`, `es`, `fr`, `it`, `ja`, `nl`, `pl`, `pt-BR`, `zh-hans`) is typed `TranslationDeepObject<typeof en>` with no partiality, so typecheck fails until all of them carry the new keys. Hand-added values are fine for dev-only strings; the ChatGPT-driven `scripts/generateTranslations.ts` is the production path and overkill here.

Deliberately **not** touched: `src/libs/ApiUtils.ts`. Flipping the global API root at a staging-style toggle would point the entire app at a mock that returns `{jsonCode: 200, mock: true}` for everything — the app would just break noisily. The probe button exercises the same `HttpUtils` code path in isolation. The `getApiRoot` branch + toggle is the first task of the *real* integration, once a QA backend that returns real data exists.

## 3. Order of work + verification

Each stage maps to a `Web_POC.md` §6 criterion:

1. **Unit tests first** (jest, `npm run test`) — the changes touch the shared network layer, so one PKCE test isn't enough. Each case guards a specific invariant:
   - `pkce.ts`: RFC 7636 Appendix B known vector + a **deterministic** regeneration-guard test (a controlled `sha256` mock returns a bad-leading digest first, then a good one — random sampling would let a deleted guard pass ≈20% of the time). Jest resolves `.native.ts` first under the repo's `jest-expo` preset (haste platforms include `native`), so tests `jest.mock` the `getWebCrypto` provider (Node's `webcrypto` for the real-digest cases).
   - `isQAServerRequest`: table test — exact QA origin passes; lookalike host (`evil-<worker-host>`), same host over http, different port, QA-host-as-substring, partial configs (in both directions), and http/malformed config values all fail. This is the security boundary deciding where the bearer goes; it's also the cheapest place to prove it.
   - `oauthClient`: response validation (terminal vs transient error codes, malformed 2xx, `token_type` must be `bearer`) *and* request construction — the outgoing param shapes (`S256`, origin-form `resource`, refresh omitting `resource`) were verified live once and only the tests keep them pinned.
   - Session action: single-flight refresh/auth (N parallel 401s → exactly one refresh, and rotated token persisted *before* any joiner resolves — this invariant lives here, not in the `HttpUtils` suite, which mocks the session action), terminal-vs-transient refresh outcomes, callback validation (state-first, error, missing code), cancel → immediate retry staying pre-warmed, and a native import-safety smoke (jest's haste config resolves `.native.ts`, so importing the graph exercises exactly what native would load). Plus the severed-opener recovery pair: a breadcrumb `storage` event completing a flow whose popup promise never settles (with `dismissAuthSession` cleaning up the dangling session), and the poll catching a breadcrumb written before the watcher attached — the storage event only fires for later writes.
   - `popupCompletionRecovery` self-close: the gate table — closes exactly the openerless, completed, callback-path popup; never the main window (wrong path), never mid-flow (no breadcrumb yet), never with a live opener, never unconfigured.
   - `HttpUtils` (extend the existing `tests/unit/HttpUtilsTest.ts`, fetch mocked, session action mocked): bearer attached on the QA origin only; `credentials: 'omit'` present on QA and non-QA requests alike; retry happens exactly once; a second 401 drops the session and rejects with the re-auth error; transient refresh failures propagate as themselves; retry side effects (`alertUser`) fire exactly once; non-QA 401 behavior unchanged.
   - `CloudflareProbe`: the decision tree in isolation — cancel → `cancelled` with no request, terminal proactive refresh → `reauthRequired` with no popup, transient refresh → `error` with the session kept, `CF_REAUTH_REQUIRED` from the request → `reauthRequired`, popup/exchange failures → semantic `error`, nothing escapes as an unhandled rejection.
   - Export state: beyond the classification gate (§2), one behavioral case proving a populated `cfSession` is actually removed from exported output.
   - Deliberately *not* automated: popup mechanics (jsdom can't simulate blockers/activation meaningfully — stage 2 covers them live) and the `TestToolMenu` wiring itself (dev-only screen; its gating logic is pinned at the probe/session level, and every manual stage exercises the wiring live).
2. **Happy path (live)**: clean browser profile → Troubleshoot page → probe with no session → popup opens **directly from the press** (this verifies the user-activation constraint from §0 — a regression that fetches first shows up as `ERR_WEB_BROWSER_BLOCKED`) → One-time PIN → Access's "Authorize Client" consent screen → popup closes itself → probe resolves with `authenticatedVia: "Cloudflare Access"`. On later re-auths (after Clear or sign-out) a still-valid Access SSO cookie skips the PIN, but the consent screen re-appears every time — each press is a brand-new authorization request, so the extra click is normal public-client behavior, not a bug (verified live Jul 27). Scope: desktop popup-capable browsers; the full-page-redirect + `sessionStorage` fallback stays a documented contingency (`Web_POC.md` §7.5), built only if popups prove unreliable. Since the severed-opener fix (Jul 27): even when the popup comes back openerless — live this hung the flow on an endless spinner — the probe now completes via the localStorage breadcrumb within about a second and the popup closes itself; `gib.js` / push-notification-chunk console errors inside the popup are known cosmetics of the short-lived boot (`Web_POC_ExpoWebBrowser.md` §2), not failures.
3. **Silent refresh**: corrupt/expire the stored access token (Onyx debug or wait out the 15 min) → probe again → exactly one token-endpoint call, no popup, rotated refresh token visible in Onyx, probe succeeds.
4. **Negative checks** (DevTools network tab): regular Expensify API calls carry no `Authorization` bearer from us; Worker calls carry no cookies; `credentials: 'omit'` intact everywhere.
5. **Sign-out, the real one**: log out of the app (not just the Clear button) — `CF_SESSION` is not in the logout preserve-list, so `Onyx.clear()` should wipe it for free, and the `SessionCleanup` callback drops the module cache; verify both, then verify the next probe re-prompts. Known papercut, documented rather than fixed: an exchange/refresh resolving mid-logout could write the session back (§7). The Clear button remains for quick iteration. Optional stretch: two tabs racing a refresh, to observe the rotation loser (documents the `Web_POC.md` §5.7 papercut, doesn't fix it).

After each edit: `npm run fmt`, `npm run lint-changed`, `npm run typecheck-tsgo`, and `npm run react-compiler-compliance-check check-changed` for the `TestToolMenu.tsx` change. Before calling the spike done: one full `npm run typecheck` — tsc is the CI gate, tsgo is only the fast dev loop.

## 4. Adding testers — email addresses only, no app changes

For people who just need to *run the flow* (sign in through the popup and hit the Worker):

1. Zero Trust → **Access controls → Policies** → `<worker> - Production` → **Include → Emails** → add their addresses. That's the whole thing — One-time PIN works for any mailbox, no IdP or Cloudflare account needed on their side. (Our org already has email-code login working; note for from-scratch reproduction: per current CF docs, *new* Zero Trust orgs no longer get the One-time PIN method automatically — add it under Zero Trust → Integrations → Identity providers → Add → One-time PIN.)
2. Seats: the free Zero Trust plan includes **50 users**; a seat is consumed on a person's first login and can be freed under Zero Trust → **My Team → Users**.
3. App side: hand them the `.env` values (the three `QA_*` keys — same file for everyone, the `client_id` is shared by design) to drop into their checkout, then restart `npm run web`. They run the standard dev origin `https://dev.new.expensify.com:8082`, so the runtime-derived redirect URI matches the registered one automatically.
4. **Mind the port.** If 8082 is already taken, the dev server silently falls back to 8083 — a *different origin*, which breaks the registered redirect URI, the Worker's CORS allowlist, and even local Onyx state (IndexedDB is keyed by origin). Free up 8082 rather than accepting the fallback.

(If the list grows past a handful of emails, an "Emails ending in `@swmansion.com`" include rule is one line — but it admits the whole domain, so explicit emails are the better default for a POC.)

## 5. Pushing the branch publicly — what actually gates access

- The branch carries the mechanism only: code, `.env.example` key names, docs. The pointers — worker host, team domain, `client_id` — travel in the `.env` file you hand out privately.
- Be honest about what the `.env` split protects: these values are **identifiers, not secrets**. The actual gate is the Access policy — someone who somehow obtained all three values but whose email isn't in the policy still can't mint a token; that's the Zero Trust model this whole POC verified. Keeping the values off the public branch is hygiene (it avoids advertising a personal Cloudflare account's endpoints and invites less drive-by probing), not the security boundary.
- Three leak vectors to close before pushing:
  1. **The docs.** `Web_POC.md` §4 and its findings contain the live values verbatim (this plan no longer does). The doc is currently untracked — keep it uncommitted, or scrub values back to `<team>` / `<worker-host>` / `<client_id>` placeholders before committing anything.
  2. **The HTTPS private key.** `config/webpack/key.pem` + `certificate.pem` sit untracked in the worktree and are **not** gitignored — `.gitignore` only covers `config/rsbuild/*.pem` — so a careless `git add -A` would stage a private key. Before pushing: regenerate/move them under `config/rsbuild/` (the ignored location) or extend `.gitignore` with `config/webpack/*.pem`. Unrelated to this POC's code, but it lives in the same tree.
  3. **Stray terminal history / `/tmp` token files** from the manual verification — the teardown list at the end of `Web_POC.md` §7 covers those.
- Known caveat, acceptable by design: rsbuild inlines the parsed `.env` into the served JS bundle, so anyone you serve a built bundle to can read the values in DevTools. Same story as above — fine, because the values aren't the gate.

## 6. Giving people access to the Cloudflare project itself — yes, possible

Account membership is separate from tester seats and works on the free plan:

1. Cloudflare dashboard (not Zero Trust) → **Manage Account → Members → Invite** → enter emails → pick roles. Invitees need their own (free) Cloudflare login and go through the email invitation — the "Skip email confirmation" shortcut for existing Cloudflare users is **Enterprise-only** (per current CF docs).
2. **Roles.** The recommended grant for collaborators is **Administrator**: the full account — Workers code, Access applications, policies, Managed OAuth settings, Zero Trust config — everything *except* billing and member management, which stay with you. Current CF docs also describe inviting an additional **Super Administrator** (that role adds billing + member management, and Super Admins can revoke each other), so literal full access is available if someone truly needs it — for a POC account, Administrator is the better default precisely because it withholds those two. Tighter alternatives from the role catalog if you want least-privilege: **Cloudflare Zero Trust** (all ZT products incl. Access) + **Workers Platform Admin** (Workers/Pages/KV/R2) together cover everything this POC touches.
3. The lists compose: a collaborator who also wants to *test* needs the member invite (§6), their email in the Access policy (§4), and the `.env` handout (§4.3).
4. Caveat worth saying out loud: Administrators can edit and delete everything except billing/members — fine for this throwaway POC account, but it's the reason not to reuse this account for anything real later.

## 7. Out of scope here, queued for the real integration

- `SHOULD_USE_QA_SERVER` toggle mirroring the staging pattern in `ApiUtils.getApiRoot` (needs a real QA backend).
- A committed `.env.qa` build variant + URL-based environment auto-detection (the POC's `QA_*` keys in the private dev `.env` are the stopgap for exactly that); production CSP `connect-src` for the team domain + QA host.
- Hardening the logout race: an in-flight code exchange or refresh that resolves after `Onyx.clear()` can write `cfSession` back (stage 5 verifies the happy logout path; the race fix — e.g. a generation counter invalidating in-flight flows — is production work).
- The full-page-redirect + `sessionStorage` fallback for popup-hostile browsers (documented contingency; build only if stage 2 shows popups are unreliable).
- Native side: `react-native-quick-crypto` + `react-native-quick-base64` install, `getWebCrypto/index.native.ts` implementation, callback interception in `linkingConfig/subscribe.ts` (Plaid pattern).
- A static, non-bundle callback page so the popup doesn't boot all of NewDot just to close itself.
- Cross-tab refresh coordination (accepted papercut per `Web_POC.md` §5.7).
